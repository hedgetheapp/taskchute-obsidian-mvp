# v0.6.64 Candidate Notes

Status: implementation candidate for review. Not committed, tagged, pushed, or distributed.

## Problem

v0.6.63 created an interrupt continuation before the interrupting task completed its task-start section move. In the T-0635 / T-0636 fixture, TaskCreated seq 2325 placed continuation E-20260816-0010 in afternoon, then TaskMoved seq 2326 moved only interrupt entry E-20260816-0009 to morning. Dev, remote, and mobile therefore ended with the continuation stranded in the old section.

## Candidate Change

- `closeRunningTaskForInterrupt()` reserves continuation identity and records TaskStopped, but does not create or publish a provisional continuation.
- `startTask()` first confirms the interrupting task's final task-start placement and TaskMoved handoff.
- `finalizeInterruptContinuationAfterStartPlacement()` creates the continuation directly after the final interrupt entry.
- The continuation row receives `section` / `section_id` from the physical heading.
- Post-save verification checks exact entry identities, task identity, same physical section, adjacency, and row metadata before TaskCreated enqueue.
- Inbound explicit continuation TaskCreated requires an exact anchor entry ID on the payload date, blocks missing / ambiguous / wrong-task / wrong-section anchors before save, and performs the same placement verification before Ack.
- Routine continuation metadata and lifecycle identity fields remain preserved.
- Unconfirmed start placement suppresses continuation row creation. Failed placement, save, verification, or enqueue is diagnosed and is not silently sent.
