## Problem

v0.6.64 correctly created the interrupt continuation at the final physical placement, but the earlier TaskMoved v4 retained the valid intermediate target order from before continuation creation. At send time, generic strict preflight compared that payload with the current section order including the later continuation and rejected the TaskMoved as stale. The later TaskCreated and TaskStarted therefore remained pending.

## Candidate Change

- Keep generic TaskMoved v4 exact-order validation unchanged.
- Limit projection to `taskmoved_payload_source=task-start-section-move-confirmed-markdown-v3`, then find a later, sendable `creation_source=interrupt-continuation` TaskCreated in the outbox.
- Require one exact match for logical clock, date, target section, anchor entry, continuation entry/task identity, and physical adjacency.
- Temporarily remove only that continuation entry from the current target order and compare the projected intermediate order strictly with the TaskMoved payload.
- Do not mutate `target_order_entry_ids` or refer to the future continuation from the earlier TaskMoved payload.
- Recompute and verify the projection after index rebuild before allowing send.
- Fall back to generic strict comparison for missing, ambiguous, stale, unrelated, or inconsistent candidates.
